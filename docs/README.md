## 自己PR

　**課題解決のスピードとリーダーシップ**が最大の強みです。難易度の高いプロジェクトへの複数回の参画経験を通じ、同時に複数の課題を抱える状況でも最短で価値を届ける技術判断力を磨いてきました。業務開始・終了時に各 10 分の PDCA 時間を設け、1 つの課題への集中を徹底することで個人の課題解決速度を向上させ、**タスク完了速度を体感で 20〜30% 向上**させてきました。チームリーダーとしては課題の優先度・緊急度を明示しながらメンバーへ指示し、**複数プロジェクトにわたってクリティカルパスの遅延をゼロに抑えてきました**。ソフトバンクでの商材出荷システム開発では、運用保守ベンダー見積りの 4 ヵ月から**2 ヵ月（工数 50% 削減）**で完成させた実績があります。対向システムとの早期疎通・全員のシステム理解底上げという技術判断が、チーム全体の手戻りを排除した結果です。
　**技術判断力とビジネスインパクトへの貢献**も強みです。エンジニアが感じる生産性・品質上のリスクをチームで可視化し、技術的負債として組織的に管理する仕組みを導入することで、開発速度の継続的な維持を実現してきました。また、CI パイプラインの高速化（30 分→12 分、**60% 削減**）や PubNub→Centrifugo 移行による外部 SaaS コスト削減など、計測に基づく技術判断でビジネスコストに直結する成果を出し続けています。新規 SaaS プロダクトでは 1 人で設計・実装・運用の全工程を担い、**250 名規模の本番利用**を実現。こうした実績に対し、会社からシニア/テックリード相当として継続的に評価されています。

## 個人のミッション

　**組織全体の生産性を仕組みで底上げすること**をミッションと考えています。
　タスク管理ツールの導入による課題可視化、情報の資料化と検索性向上、アジェンダ・議事録による会議コストの削減など、チーム運営の基盤を整えることで組織の無駄な工数を削減してきました。ソフトバンクでの **50 名規模 LeSS（大規模スクラム）プロジェクト**では、開発者全員が抱える生産性・品質リスクを可視化し、技術的負債の棚卸・管理の場をファシリテーション。「上から言われた問題」ではなく「自分たちで挙げた問題」として扱うことで、メンバーが高いモチベーションで自律的に課題解決に向かう組織文化を醸成しました。また、チーム間の技術相談コストを削減する「トラベラー」役割を設計・運用し、横断的な品質管理体制を構築した実績があります。
　技術面でも同様の考えを実践しています。CI パイプラインの高速化（**30 分→12 分・実行時間 60% 削減**）はチーム全エンジニアの待機コストを組織横断で削減し、開発フィードバックループを加速させました。静的解析・SonarQube・Sentry/Datadog APM の導入で個人の勘に頼らない品質維持の仕組みを構築。PubNub→Centrifugo 移行では外部 SaaS への依存を排除し、コストと運用自由度を同時に改善しています。ドメイン駆動設計を意識した設計勉強会への登壇も継続し、チームの長期的な設計品質向上に組織資産として投資しています。
　生産性を上げる方法は個人に依存することが多いですが、生産性を下げない方法は仕組みで防ぐことが可能でした。誰かが意識しなければすぐに悪習が蔓延り、生産性を下げないための仕組みは陳腐化してしまいます。1 人が短期的に 1.1 倍の生産性を出せるようにするのではなく、**100 人が長期的に 1.01 倍の生産性を出せるようにする**。これを体現した具体的取り組みが、CI 高速化によるチーム全員への恩恵、50 名規模での技術的負債管理の仕組み化、設計勉強会による知識の組織資産化です。それが私に与えられたミッションだと考えて、常日頃から行動しております。

#### 社内審査システムのAPI開発

|期間|規模|役割|
|---|---|---|
|2020/08～2020/12|1 名|フルスタックエンジニア|

- 技術スタック
    - Java, Spring, PostgreSQL
    - Jenkins, Ansible, Docker
    - SonarQube, Open API
- 担当業務

SOAP 連携しか用意されていない審査システムに対して、REST API でも連携できるようにするための中間層となるシステムです。同時期に当システムの API を実行するプロジェクトも進行していましたので、そのプロジェクトとも連携を取りながら進行しました。

設計・開発を担当。設計を含めて開発期間は 1 ヵ月だったため、あらゆる工程を薄く結合することを意識しました。例えばサーバを用意したのち、まずはエンドポイントのみを作成いたしました。対向システムとの疎通確認を行うことで、環境設定に不備がないかを確認しています。続いて、用意したサーバから審査システムに対して cURL で SOAP 連携が可能かを検証しました。さらに、電文を対象審査システムにて、どのように画面表示されるかも確認しました。この例のように、徹底的に薄く結合することを意識して作業を行いました。

環境設定は別の部署で一括管理していることもあり、依頼から設定完了までのリードタイムを気にして行動しました。ファイアウォール等の環境設定だけでなく、影響する対向システムのアカウントを早期に発効してもらって操作方法を教えてもらい、画面を含めた一気通貫で動作確認できる状態を早期に作り上げました。このように行動した経緯として、過去の経験からまずは自システムの作りこみに集中してしまうことが多くありました。全ての機能を設計書の通りに作成し、それから結合することは進捗管理としては誤りではありません。しかし、対向システムが存在する場合は、対向システムが受け取った結果が正しいものとなります。対向システムが受け取った結果を開発者が画面で確認しなかったために、より後の工程で不具合が発覚し、手戻りが発生することが多々ありました。

進捗管理としては複雑にはなってしまいましたが、内部の作り込みよりもインタフェース面での確認を強く意識しながら進めた結果、当システム起因でのプロジェクト遅延や障害は発生しませんでした。

社内表彰されるほどの評価もされたプロジェクトです。
