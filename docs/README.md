## 自己PR

### 業務の「なぜ」まで理解して仕様に落とす

　官公庁の法令作成業務から、法人向けの販売・出荷・審査といった商流、1on1 支援 SaaS まで、複数の業務領域で要件定義から運用までを一気通貫で担当してきました。表面的な仕様をなぞるのではなく、その業務が求められる背景まで踏み込んで理解したうえで仕様を組み立てます。思想の異なる 2 つの販売系システムを 1 回の API 呼び出しで連携させる案件では、双方のライフサイクルを両立させるデータの持ち方を設計して実現しました。

### つくって終わりにせず、動かしきる

　開発を「つくる」だけで終わらせず、「動かしきる・成果を出しきる」ところまで責任を持ちます。対向システムがある開発では、自システムを作り込む前に相手システムと疎通できる状態をつくり、インタフェースの確認を最優先にしてきました。この進め方で、運用保守ベンダーが 4 ヵ月と見積もった API 開発を 2 ヵ月で完成させています。別の API 開発でも、当該システム起因の遅延や障害をゼロに抑えました。社長賞を含む社内表彰も複数回いただいています。

### 完遂力をコードから組織へ広げる

　直近は 1on1 支援 SaaS の開発責任者として、この完遂力を組織に向けました。コミュニケーション支援を事業とする会社の開発組織が、コミュニケーションを遠ざける構造になっていたためです。開発・PdM・QA・デザイナーで構成するクロスファンクショナルチームを導入し、リリース遅延を半分ほどに減らしました。あわせて生成 AI を前提に開発プロセスを再設計し、AI が検証をループで回したあとに人間が不足観点をレビューする体制へ移行させています。現在はテックリードとして、中核製品のリニューアルで AI 機能とデータ集計基盤の開発をリードしています。

## 個人のミッション

　**1 人が短期的に 1.1 倍の生産性を出すより、100 人が長期的に 1.01 倍の生産性を出せる仕組みをつくる。** これが私のミッションです。

　生産性を上げる方法は個人に依存しがちですが、生産性を下げない方法は仕組みで守れます。ただし誰かが意識し続けなければ、悪習はすぐに広がり、仕組みも陳腐化します。だからこそ業務を完遂するだけでなく、チーム全体の生産性を下げないための仕組みづくりまでを自分の役割と考えています。

　日々の運用では、タスク管理ツールの導入、参照しやすい形での情報の資料化、アジェンダとタイムテーブルを用意した会議運営と議事録の共有を徹底します。技術面では、失敗に早く気付いて手戻りを減らす CI/CD や、個人の勘に頼らず障害を未然に防ぐ静的解析を導入してきました。設計ではドメイン駆動設計を意識し、目先ではなく数年先の生産性を見据えて判断しています。設計をテーマにした勉強会で登壇もしています。

#### 開発責任者として組織とプロセスを再設計

|期間|規模|役割|
|---|---|---|
|2025/05～2025/12|〜25 名|開発責任者|

最大 25 名規模の開発組織のオーナーとして、組織設計・採用・生成 AI の組織導入を推進しました。

- **課題認識**

従来はチケット駆動開発を採用していました。PdM が要望を起票し、私がブラッシュアップしたうえで、PdM リーダーと 2 人でエンジニアにアサインする体制です。コミュニケーションコストが最小で済む反面、各エンジニアに高い自走力を求める仕組みでした。開発力をスケールさせるために人数を増やすと、課題を 1 人で抱え込むメンバーが出てきました。さらに各自が自分のタスクしか見ないため、朝会は報告だけの場になり、互いに助け合わない状態が生まれていました。コミュニケーション支援を事業とする会社の開発組織が、コミュニケーションを遠ざける構造になっている。この点を特に問題視しました。

- **クロスファンクショナルチームの導入**

開発・PdM・QA・デザイナーを 1 つのチームにまとめたクロスファンクショナルチームを設計・導入しました。職能を混ぜることで、助け合いとコミュニケーションが自然と生まれる土壌をつくりました。同時にチームを適切な単位に分け、コミュニケーションコストが必要以上に増えることも防いでいます。チームビルディングとして XP（エクストリームプログラミング）の輪読会を実施し、2 週間スプリントのスクラムを導入しました。

以前は誰もアラートを上げないままリリースが遅れることもありました。チーム化後は遅延の兆しを早い段階で検知できるようになり、リリース遅延は半分ほどまで減っています。

- **生成 AI の組織導入と開発プロセスの再設計**

運用面では Devin を導入し、仕様や不具合の問い合わせ対応を効率化して開発の中断を減らしました。開発面では Codex と Claude Code を導入し、ツールの導入にとどまらず開発プロセスそのものを再設計しています。

Claude Code のプラグイン共有と、ADR・Design Doc・PRD・openspec による事前のドキュメント作成を仕組み化しました。考慮漏れを減らし、生成 AI の出力のブレを抑えています。

コードレビューのプロセスも再設計しました。従来は人間がコードを直接レビューしていました。現在は検証環境へのデプロイ後、AI が Playwright CLI や AgentBrowser を使ってテストケースを洗い出し、実行します。AWS CLI と Datadog で監視しながら問題がなくなるまで AI にループさせ、人間は最後に不足観点がないかをレビューする体制へ移行しています。

- **その他の取り組み**
    - エンジニア採用を主導
    - 自社プロダクトのドッグフーディングも兼ねて、正社員とは 2 週間に 1 回、業務委託メンバーとは 1 ヵ月に 1 回の 1on1 を実施

#### 中核製品の継続開発（フルスタック）

|期間|規模|役割|
|---|---|---|
|2023/11～現在|〜25 名|フルスタック開発者|

- 技術スタック
    - Ruby on Rails, Python (FastAPI), TypeScript/Angular
    - MySQL, GraphQL, Docker
- 担当業務

1on1 支援 SaaS の中核製品を、コア機能からエンタープライズ要件・データ整合性まで横断して継続開発しています。代表的な領域は次のとおりです。

- **エンタープライズ認証基盤**: SSO/SAML 設定の管理画面化、2 要素認証（TOTP）、Google SSO（OAuth）からのカレンダー自動連携。IP アドレス制限などの個別要件にも対応
- **マルチテナント統合**: 複数ワークスペースを 1 つに統合する要件で、既存データ（1on1 記録・感想・ユーザー）を欠損・重複なく移行・集約。約 2 ヵ月で 10 ワークスペースをデータロスト 0・無停止で統合
    - 移行戦略：過去分のデータも含めて統合先へコピーする方式を採用
    - ロールバック設計：統合前後のデータを対応付ける中間マッピングレコードを保持し、問題発生時には統合分だけを削除して切り戻せる状態を確保
    - 検証：ユースケースを洗い出し、データ不整合が出ないことを確認
- **集約機能**: 組織構造に沿った集計の CSV 一括設定、ペア単位集計、組織変更への追従、削除データの整合性担保まで継続してオーナーシップを持つ
- **メンター・メンティマッチング**: 自動マッチングの無限ループ回避、レコードロックに依存しない重複起動制御、削除時のデータ整合性の堅牢化。リリース後に 5 社が導入
- **定期フィードバック集計機能**: 0→1 で実装して Lambda による月次自動実行に乗せ、集計ロジックの不具合（割合 100％超過）まで是正
- カレンダー連携（Google/Outlook）、満足度・サーベイ集計、管理画面・CSV 入出力など

- **生成 AI 前提の開発・運用の仕組み（2026）**: 調査・複数モデルでの相互レビュー・リリース後の監視・リリース対象の洗い出しを、チーム共通の Claude Code スキルとして整備。問い合わせ調査の結果をナレッジリポジトリへ書き戻す運用を確立

VB6・.NET ともにこのプロジェクトで初めて触れ、DB も Postgres の経験しかなかったため Oracle での開発は初めてでした。この経験で新しい言語を学ぶことへの障壁がなくなり、自己学習で Python を使った機械学習などにも取り組むようになりました。

最大の変更点は、VB6 から .NET への言語の差異ではなく、oo4o から ODP.NET への DB 接続ミドルウェアの差異でした。oo4o では編集メソッドで行ロックがかかっていましたが、ODP.NET には同等のメソッドがなく、明示的な行ロックが必要でした。

言語やミドルウェアが生まれた背景にある時流や思想まで掴むことで、単なる経験にとどまらず、新しい技術に向き合うときにも応用できることを学びました。

本プロジェクトは社内で社長賞を受賞しました。


#### 法案承認する官公庁システムの新規作成


|期間|規模|役割|
|---|---|---|
|2015/01～2016/03|6-12 名|メンバー|

- 技術スタック
    - Java, Spring, jQuery
- 担当業務

各官公庁で個別に行われていた法律作成業務を 1 つのシステムで共通化し、残業時間を減らすことを目的にフルスクラッチで開発したシステムです。霞が関の働き方改革の例として、日本経済新聞でも紹介されました。

2 次受けとして参画し、ウォーターフォールで要件定義からリリースまでのサイクルを 2 回経験しました。jQuery による Ajax 通信、Spring の DI、Hibernate による O/R マッピングなど、開発の基礎をここで身につけました。Hibernate は日本語の文献が少なかったため、公式ドキュメントを日本語に訳して資料化しました。1 回目のサイクルで作った資料を 2 回目に増員されたメンバーへ渡すことで、全体の工数削減につなげました。

責任者が現場にいないことが多く、情報は必要な人員だけに共有され、全体へ周知する時間が取れていませんでした。そこで、立ち上げから参画して全体仕様を把握し、PM とも近い立場だった私が情報を集約しました。協力会社へ周知して内容の再確認を徹底した結果、早期対応によって工数を削減できたと考えています。
